# PayGuard 讲解式端到端处置系统设计

## 1. 目标与边界

PayGuard 面向支付宝三方商户故障保障场景，完整覆盖故障核验、定位分析、商户触达、故障升级、恢复判断和智能化评测。默认使用 3–5 分钟的屏幕共享讲解场景：演示者每点击一次只推进一个业务步骤，页面同步呈现输入、AI 动作、工具调用、结构化结果、阶段指标和风险控制。

系统不展示候选人信息、个人经历或岗位匹配评分。系统对职位要求的覆盖由真实可操作的功能、数据口径和评测闭环直接体现。

首版不连接真实支付生产系统。它提供确定性的 Mock Runtime，并定义可替换的 HTTP Runtime 合约。Mock 与真实运行模式共享状态机、数据结构、页面组件和评测指标，避免把演示实现成一套不可复用的动画。

## 2. 核心体验

默认首页为「处置演示」，而不是全局运营大屏。页面围绕一条 P0 商户接口超时事故展开，首屏只保留与当前事故有关的信息。

页面分为四个区域：

1. 顶部事故摘要：事故编号、商户、严重度、影响金额、运行模式、当前进度和重置入口。
2. 左侧步骤轨道：智能核验、定位分析、商户触达、故障升级、恢复判断、评测回流六个步骤。
3. 中央执行区：展示当前步骤的业务目标、输入、工具调用时间线、决策依据和结构化输出。
4. 右侧设计区：展示进入条件、成功指标、风险控制、异常路径和下一步动作。

底部固定显示本次事故的累计耗时、Token、成本、工具调用次数、证据数量和人工介入次数。

演示操作遵循以下规则：

- 每次点击只完成一个步骤，不使用自动播放和自动计时推进。
- 支持返回已完成步骤查看历史结果，但返回查看不会回滚事故状态。
- 支持重置并从相同初始数据重新演示。
- 商户触达必须经过人工批准；拒绝发送时进入人工接管分支。
- 工具超时、低置信度和证据不足均有明确的降级状态。
- 页面刷新后从本地存储恢复演示进度。

## 3. 六步端到端流程

### 3.1 智能核验

业务目标：判断告警是否为真实故障，消除瞬时流量波动、重复告警和单指标误报。

输入包括支付成功率、接口 P95 RT、TIMEOUT 错误码、流量基线、告警窗口和商户基础信息。系统调用 Metrics 和 Alert Context 工具，输出 `isIncident`、严重等级、影响范围、置信度和证据引用。

进入下一步的条件是 `isIncident = true` 且证据完整度达到阈值。低置信度结果进入人工核验分支。

### 3.2 定位分析

业务目标：从指标、日志、变更和历史案例中识别最可能的根因，并提供可审计证据。

系统依次调用 Metrics、Logs、Change Records 和 Case RAG，输出 Top-3 根因、各自置信度、支持证据、反证和建议排查动作。页面只展示结构化决策因素，不展示模型内部思维链。

进入下一步的条件是 Top-1 根因置信度和 Evidence Grounding 达标；否则标记为需要人工定位。

### 3.3 商户触达

业务目标：根据事故等级、商户画像和已确认事实生成准确、可执行的沟通内容。

系统调用 Merchant Profile 和 Message Composer，生成站内信预览、排查建议、预计恢复时间和回执链接。发送属于高影响动作，必须由演示者点击「批准并发送」后执行。拒绝时记录人工接管原因，不伪造发送结果。

触达结果包含送达、打开、点击和回复事件，供后续漏斗与效果评测使用。

### 3.4 故障升级

业务目标：依据影响金额、影响商户数、严重度、持续时间和恢复进展匹配升级策略。

系统调用 Policy Engine、On-call Directory 和 Ticket 工具，输出升级等级、责任团队、SLA、工单编号和通知对象。所有 Mock 外部动作均标记为仿真操作。

### 3.5 恢复判断

业务目标：确认故障真正恢复，避免因指标短暂回弹而提前关闭事故。

系统读取连续三个观测窗口，对支付成功率、P95 RT、错误码和流量进行基线比较，输出 `recovered`、稳定窗口数、残余风险和观察建议。只有连续窗口均达标才允许关闭事故。

### 3.6 评测回流

业务目标：把处置结果转化为可持续优化的评测数据，而不是在恢复后终止流程。

系统汇总最终根因、人工修正、工具结果、商户反馈和恢复状态，生成评测样本并更新核验 Precision/Recall/F1、P0 Recall、根因 Top-1/Top-3、Evidence Grounding、Tool Selection Accuracy、触达点击率、人工接管率、MTTR 和单次成本。

Bad Case 会记录失败阶段、失败原因、期望结果和建议改进项，可进入后续 Prompt 或工具策略实验。

## 4. 信息架构

应用保留四个可操作模块：

- **处置演示**：默认入口，完成六步事故讲解。
- **事故中心**：筛选事故、查看状态、打开完整 Trace，并选择事故进入演示。
- **流程分析**：展示告警到恢复的漏斗、桑基图、阶段耗时、工具使用和触达转化。
- **AI 评测**：展示分类指标、分级召回、根因准确率、混淆矩阵、实验对比和 Bad Case。

删除或隐藏没有真实功能的「数据集」「Prompt 版本」「系统设置」导航项。需要展示的数据集和 Prompt 实验直接进入 AI 评测模块，减少空入口。

## 5. Runtime 架构

页面只依赖统一的 `IncidentRuntime`：

```ts
interface IncidentRuntime {
  createIncident(scenarioId: string): Promise<IncidentRun>;
  executeStage(runId: string, stage: IncidentStage): Promise<StageExecution>;
  approveAction(runId: string, actionId: string): Promise<ActionResult>;
  rejectAction(runId: string, actionId: string, reason: string): Promise<ActionResult>;
  getRun(runId: string): Promise<IncidentRun>;
  resetRun(runId: string): Promise<IncidentRun>;
}
```

实现分为：

- `MockIncidentRuntime`：读取类型化场景数据，按固定结果返回阶段事件，可配置成功、超时、低置信度和人工接管分支。
- `HttpIncidentRuntime`：按照相同接口调用后端 API。首版提供请求、响应和错误类型，不配置真实生产地址。

Runtime 通过事件返回工具调用过程，页面不直接拼装业务结果：

```text
stage_started
tool_call_started
tool_call_completed | tool_call_failed
stage_decision_ready
approval_required
stage_completed | stage_needs_human
```

该事件模型允许未来替换为 SSE 或 WebSocket 流式返回，而不改变页面的阶段组件。

## 6. 状态模型

`IncidentRun` 保存事故上下文、当前步骤、已完成步骤、阶段执行结果、待审批动作、累计指标和最终评测样本。

状态机只允许以下转换：

```text
idle → verify → locate → contact → escalate → recover → evaluate → completed
                     ↘ awaiting_approval
任意执行阶段 → needs_human | failed
```

点击「下一步」只触发当前允许的转换。重复点击、越级执行和审批缺失会被状态机拒绝，并在页面显示原因。

本地存储只保存非敏感 Mock 状态。HTTP Runtime 不把真实事故详情写入浏览器持久存储。

## 7. Mock 场景

首个黄金路径使用「星海出行支付接口超时」：

- 初始异常：支付成功率从 99.72% 降至 71.36%，P95 RT 从 126ms 升至 4,620ms，TIMEOUT 增长 23.4 倍。
- 根因：商户 API 网关连接池耗尽，与历史 Case 相似度 91.4%。
- 触达：生成 P0 故障通知与连接池排查建议，等待人工批准。
- 升级：创建 Mock 工单并通知商户保障与网关值班团队。
- 恢复：连续三个窗口恢复至基线范围后关闭事故。
- 评测：写入一条正确核验、Top-1 命中、证据完整且无人工修正的样本。

场景数据按阶段拆分，页面不能提前读取尚未执行步骤的结果。

## 8. 视觉与交互调整

- 保留深墨蓝企业工具风格，但放大正文与关键标签，降低当前页面的过度信息密度。
- 默认首屏不显示六张全局 KPI 卡和事故队列，避免稀释演示主线。
- 当前步骤使用明确的高亮边界，完成步骤使用勾选状态，未执行步骤不提前展示结果。
- 工具调用采用纵向事件流，清楚区分调用中、成功、失败和降级。
- 结构化输出同时提供摘要视图和 JSON 视图。
- 所有点击目标不小于 44px，并提供键盘焦点状态。
- 修复移动端侧栏遮挡、表格横向溢出和字体缓存旧路径问题。
- 遵守 `prefers-reduced-motion`，状态切换只使用 150–250ms 的透明度和位移动画。

## 9. 错误与降级

- 工具超时：展示超时工具、已重试次数、降级数据源和人工接管入口。
- 低置信度：禁止自动进入高影响阶段，要求人工确认。
- 审批拒绝：保存拒绝原因，转入人工处理，不继续模拟发送。
- Runtime 不可用：保留已完成 Trace，显示重试和切换 Mock 模式入口。
- 本地状态损坏：清除单次运行状态并恢复到场景选择页，不影响其他数据。
- 图表初始化失败：显示指标表格和文字摘要。

## 10. 测试与验收

单元测试覆盖：

- 六步状态机的合法与非法转换。
- 触达审批、拒绝和人工接管分支。
- Mock Runtime 的成功、超时与低置信度结果。
- 累计耗时、Token、成本和工具调用统计。
- Precision、Recall、F1、点击率和漏斗转化率口径。
- 本地状态恢复和损坏状态降级。

组件测试覆盖：

- 每次点击只推进一个步骤。
- 未执行步骤不泄露结果。
- 当前步骤正确展示输入、工具调用、输出与指标。
- 审批前无法进入升级步骤。
- 重置后恢复到初始场景。
- 四个主模块可以导航，事故详情可以下钻。

浏览器验收覆盖：

- 1280×720 下可完整展示当前步骤、进度和主要操作。
- 375px、768px 和 1440px 无侧栏遮挡或页面横向溢出。
- 完成黄金路径需要六次阶段操作和一次触达审批，且不会自动推进。
- 完成后 AI 评测模块出现本次运行生成的评测样本。
- 控制台无资源加载失败和未处理异常。
- `npm test`、`npm run types:check`、`npm run lint` 和 `npm run build` 全部通过。

## 11. 明确不做

- 不连接真实支付宝、商户、消息、工单或监控生产系统。
- 不展示模型隐藏思维链。
- 不增加登录、权限、组织管理和多租户能力。
- 不实现自动播放式演示。
- 不保留无法操作的导航和按钮。
- 不为单一 Mock 场景引入工作流引擎或数据库。
