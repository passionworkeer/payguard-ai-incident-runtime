# PayGuard 商户故障 AI 处置台设计

## 目标

构建一个面向支付宝三方商户故障场景的高保真前端 Demo。系统以轻量状态机呈现“核验、定位、触达、升级、恢复”五段 AI 处置流程，并通过可下钻的运营看板证明候选人具备 AI 产品拆解、工具调用、效果评测、SQL 指标和数据闭环能力。

首版只使用可解释的合成数据，不接真实支付、监控或模型 API。所有数据结构保留未来接入后端的边界。

## 演示主线

1. 用户进入驾驶舱，看见当前故障态势、AI 自动化效果和业务影响。
2. 用户点击“注入模拟故障”，生成一个“商户接口超时”事件。
3. 事件沿五段状态机推进，每段展示状态、AI 耗时、工具调用、Token、成本、置信度、输入输出和人工介入。
4. 用户打开事故详情，查看指标、日志、历史案例和结构化证据，并审批商户触达内容。
5. 用户切换到分析页，通过漏斗、桑基图、趋势图、混淆矩阵和耗时分布解释系统效果。
6. 用户切换模型或 Prompt 版本，查看核验召回率、根因准确率、人工接管率、MTTR 和成本的实验差异。

## 信息架构

应用包含四个主视图，均位于单页应用内：

- **运营总览**：全局 KPI、实时事故流程、业务趋势、环节健康度和重点事故。
- **流程分析**：全链路漏斗、告警去向桑基图、阶段耗时、工具使用率、触达点击率和恢复分布。
- **AI 评测**：混淆矩阵、分级 Precision/Recall、根因 Top-K、Prompt/模型实验、Bad Case 列表。
- **事故中心**：可筛选事故表格，以及点击后出现的事故详情抽屉。

全局顶栏提供时间范围、商户层级、模型版本、自动刷新状态和“注入模拟故障”入口。

## 核心界面

### 运营总览

首屏采用深色企业运营驾驶舱风格，避免霓虹科技大屏。视觉重点是清晰层级、紧凑信息密度和可信的数据标注。

顶部 KPI 包含：

- 活跃事故数：7
- AI 自动处置率：78.4%
- P0 故障召回率：98.7%
- 平均恢复时长：18.6 分钟，较基线下降 34.2%
- 商户触达点击率：64.8%
- 单事故 AI 成本：¥0.42

核心流程卡按核验、定位、触达、升级、恢复排列。每张卡展示当前队列、成功率、P50/P95 耗时、人工接管率和最近一次 Agent 动作。流程上方显示当前 Incident，阶段切换有轻量动画。

### 流程分析

- **漏斗图**：12,847 条原始告警 → 3,982 条候选事件 → 2,194 条真实故障 → 1,876 条成功定位 → 1,522 条成功触达 → 1,439 条确认恢复。
- **桑基图**：告警来源 → 核验结果 → 根因类别 → 处置动作 → 恢复结果，支持点击节点过滤其他图表。
- **阶段耗时图**：按五阶段比较 P50、P95 和 SLA，突出定位阶段的长尾。
- **触达分析**：发送、送达、打开、点击、回复的渠道漏斗，并比较站内信、短信和电话。
- **工具使用率**：Metrics、Logs、Case RAG、Merchant Profile、Ticket、Message 六类工具的调用量、成功率和贡献度。

### AI 评测

- 核验混淆矩阵与 Precision、Recall、F1。
- P0/P1/P2 分级召回率，P0 目标线为 99%。
- 根因 Top-1/Top-3 Accuracy。
- Evidence Grounding、Tool Selection Accuracy、Hallucination Rate。
- Baseline Rule、RAG Agent、Evidence Agent 三组实验对比。
- Bad Case 表格支持按阶段、严重度和失败原因筛选。

### 事故详情抽屉

抽屉包含：

- 事故标题、商户、等级、影响金额、开始时间和当前状态。
- 五阶段纵向 Timeline；每阶段展开后显示耗时、Token、成本、工具调用和结构化输出。
- 指标证据：支付成功率、接口 RT、错误码倍率和流量变化。
- 日志证据与历史相似案例。
- 根因、置信度、证据引用和推荐动作。
- 商户触达文案预览，以及“批准发送”和“人工接管”操作。

## 数据模型

`Incident` 是页面的主实体，包含业务字段、当前阶段、五段 Trace、证据、触达结果和恢复状态。

`StageTrace` 包含：

- `stage`：verify、locate、contact、escalate、recover
- `status`：queued、running、success、needs_review、failed
- `latencyMs`、`inputTokens`、`outputTokens`、`costYuan`
- `confidence`、`toolCalls`、`humanOverride`
- `summary`、`evidenceIds`、`startedAt`、`completedAt`

`AnalyticsSnapshot` 保存漏斗、桑基图、时间序列、分级指标、工具统计和实验结果。图表组件只消费明确的 ViewModel，不直接计算业务口径。

## 指标口径

- AI 自动处置率 = 无人工接管并完成恢复的事故数 / 已恢复事故数。
- 商户触达点击率 = 点击详情链接的商户数 / 成功送达商户数。
- 核验 Recall = TP / (TP + FN)，P0 单独计算。
- 根因 Top-1 Accuracy = 第一候选根因正确的事故数 / 有标注事故数。
- 阶段耗时从该阶段 `startedAt` 到 `completedAt`，总 MTTR 从首次告警到恢复确认。
- 工具贡献度由该工具引用的有效证据数 / 全部有效证据数近似表示，并明确标注为解释性指标。

## 技术方案

- Vite + React + TypeScript 构建独立 SPA。
- ECharts 绘制桑基、漏斗、折线、柱状、散点、热力和仪表类图表。
- CSS Variables + 原生 CSS 实现设计系统，避免引入重型组件库。
- 页面数据来自类型化 Mock 模块；模拟故障由确定性状态机驱动。
- 分析计算放在纯函数中，通过 Vitest 单元测试锁定指标口径。
- 浏览器验收覆盖导航切换、故障注入、事故下钻、筛选联动和响应式布局。

## 视觉原则

- 深墨蓝背景、低饱和青蓝主色、琥珀色告警和珊瑚红故障色。
- 卡片边界依赖微弱明度差和 1px 描边，不使用大面积玻璃拟态。
- 数字使用等宽字体，中文正文使用系统无衬线字体。
- 每张图都显示口径、时间范围、单位、目标线或对比基线。
- 动画仅用于状态推进、筛选过渡和抽屉，不干扰读数。
- 桌面端优先，1280px 仍保持完整演示；移动端提供可读降级，不追求同等信息密度。

## 异常与降级

- 无数据时显示原因、筛选条件和重置入口，不渲染空坐标轴。
- 图表加载失败时回退为关键数字与表格摘要。
- 故障模拟可重复启动，但同一时间只运行一个活动模拟。
- 所有“发送”“升级”操作均为本地模拟并有清晰标签，避免误解为真实外部动作。

## 验收标准

- 首屏在 1440×900 视口内完整呈现核心 KPI、流程和至少两张主图。
- 四个主视图均可切换，图表与表格使用一致的数据口径。
- 可以注入一次模拟故障并看到五阶段逐步推进及逐阶段 AI 指标。
- 点击事故可查看完整 Trace、证据和触达操作。
- 至少包含漏斗、桑基、趋势、耗时分布、混淆矩阵五类图表。
- 单元测试覆盖漏斗转化率、Precision/Recall/F1、阶段耗时和触达点击率。
- `npm run build`、`npm test` 和浏览器关键路径检查通过。
